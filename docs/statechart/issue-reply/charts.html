A reply in the issue across a crash between the POST and reply.settled

Model issue_reply.tla, checked with TLC 2.19 (tla2tools 1.7.4) and drawn with the pstack statechart skill. Each state names the log fact (Kinds in harness/src/domain.ts) that stands for it. Rebuild with node docs/statechart/build.mjs issue-reply.

Rules

  • AtMostOneComment: one reply.intended gives at most one comment in the issue.
  • SettledMeansPosted: reply.settled sent means a comment exists.

Where each state and arrow is in the code

  • Pending in the outbox: reply.intended (routing.ts:174-183). The outbox is the fold outboxView: an intent stays pending until its reply.settled exists (routing.ts:43-56).
  • The daemon drains the outbox on every tick (cli.ts:48-55, cli.ts:57-65).
  • Lists the comments: send() looks for the marker harness:<intent> first (github.ts:121-128).
  • POSTs the comment: the body carries the marker (github.ts:129).
  • Settled: reply.settled with result sent (routing.ts:185-189).
  • Crash after the POST: the live proof is design/mvp/e2e/unit3/crash-after-post.ts, which POSTs and exits 137 without settling.

The broken model

MarkerLookup = FALSE. send() POSTs without first listing the issue comments for the hidden marker, so a crash after the POST and before reply.settled gives a second comment on restart.

## AtMostOneComment breaks
The shortest path has 7 steps:
0. Nothing to send yet
1. the router replies (reply.intended): Pending in the outbox (reply.intended)
2. the daemon lists the comments, no marker: No marker on GitHub, about to POST
3. the daemon POSTs the comment with the marker: Comment posted, settle not written yet
4. the daemon crashes: Daemon down after the POST, still pending (reply.intended)
5. launchd restarts the daemon: Daemon back, comment on GitHub, still pending (reply.intended)
6. the daemon lists the comments, no marker: Marker not looked up, about to POST again
7. the daemon POSTs the comment with the marker: Two comments for one intent

## Rules that hold
TypeOK, SettledMeansPosted, NoDeadlock

What the model leaves out

  • One intent, one issue, at most 2 crashes. A POST that times out after GitHub created the comment acts like a crash after the POST.
  • The gone result (HTTP 404 or 410).
  • The model has two more switches, checked outside this folder: StaleList (GitHub's list can miss a fresh comment) and a second sender.
